### 0.1 三个业务结果

**机制一：先处理已知研究分歧，再进入推荐成稿。**

新推荐与旧推荐的当日复盘，先各自形成判断；对同股、同时间、同价格、同参与目的的实质分歧，由原研究负责人处理。最后仍检查真实文章有没有把确定的判断写错。不要强行统一不同目标的意见，不改历史评价和第二十日结案。

**机制二：作者收到当前有效研究说明，而不是多轮解释的累积。**

同一轮研究只有一份当前有效含义。旧解释被取代后，不能继续混在作者材料中。保留必要证据、反证、未知和完整条件，不以少写内容制造“更简洁”的假改善。需要修订时，保留同一篇底稿、集中编辑全文，不逐个问题追加一段。

**机制三：阅读审查与事实核对实际分开供料。**

阅读审查先只收到待发表文章及阅读标准；提交判断后，另一阶段再按原研究核对事实与条件。第一阶段不能预先接触研究底稿、内部争论、用户好坏标签。两类意见集中交回作者，不互相抵消，不形成无限修改循环。

### 0.2 四项技术结果

## 3. 机制一的实施：实质分歧前移，最终文字核对保留

### 3.1 目标顺序

```text
沿用原时间身份和数据准备
→ 选股研究形成 pending trace 与初始交接
→ 正式复盘形成自身当前判断（已有同版结果直接复用）
→ 对同股进行“研究结论级”核对
→ 确有分歧，由原负责人集中处理并重核
→ 原研究负责人整理同版当前有效研究说明
→ 推荐作者成稿
→ 阅读审查 + 事实核对，集中修订一次后复核
→ 对最终真实推荐正文与复盘当前正文作文字一致性核对
→ 原有采用、正式保存、日报装配及正常 Web 渲染
```

上面不是要求额外重跑全量复盘。最小实现可以复用当前已经先行生成的复盘草稿，只提前比较其中当日判断。没有业务理由，不要把全部复盘拆成新的作者系统。

### 3.2 成稿前核对的输入和结果

新增或抽取一个**研究结论级输入构造函数**，读取：

- 本轮准确的 `formation_date`、`action_date`、带时区 `as_of` 及实际行情日。
- 新推荐的当前意见、参考价及参与范围、参与目的、观察期、触发条件、关键依据和来源。
- 同股旧推荐对应的 `current_opportunity`，及其中必要的当日判断说明；不得拿原推荐历史评价替代当前意见。
- 必须核对的实际同股组合。没有组合就直接记录无须核对，不启动模型凑步骤。

现有结构字段不足以准确表达某项判断时，取其真实当前说明，或向原负责人请求该项缺失说明；不能由程序猜测，更不能根据“偏积极”等标签直接裁决。相关复盘缺失、身份不明或截止不同，必须标为未核实，不能当成“没有同股组合”直接跳过。

成稿前不要求尚不存在的推荐正文，不制造空文章、不用虚构引句通过旧验证器。核对结果引用真实研究字段或说明原句。与成稿后核对使用不同阶段标识和缓存身份，避免互相冒用。

允许复用原核对结果类别：兼容、差异已有实际依据、尚未解决；不要新增评分和投票机制。

### 3.3 分歧由谁处理

继续沿用原研究总控/selection 与原正式复盘/monitor 负责人的边界：

- 新参与意见确有冲突，回到原截止已知证据作判断。不能默认选股方、复盘方、积极方或谨慎方正确。
- “已持有继续观察”和“尚未买入不要追入”可以并存，但必须说明各自适用对象及依据。
- 新旧推荐的持有期确实不同，可以保留差异；不能只用“周期不同”四个字敷衍。
- 第二十日结案、历史推荐得失、旧判断有没有被证实，不随当前参与意见改写。
- 若研究负责人撤回当日一只推荐，照实保留去向，不补一只股票凑数量。因文章未完成不得冒充研究撤回。
- 只修改受影响的本日 pending 结果及对应说明，保留其他股票、历史结果和原始事实。

每侧负责人接收一次集中问题，不逐项零散召回。保留现有有限处理预算；本轮成稿前允许一次集中负责人处理及一次重核，仍未解决则记录未决，不自动进入下一轮。

### 3.4 成稿后核对不能删

仍比较实际采用的推荐正文与复盘当前正文，确认作者没有改错对象、时间、条件或意见。

发现的是表达错误，回到同一篇作者修订；发现新的实质研究错误，交回原负责人。对后发现的研究错误，只做一次有明确原因的定向处理，计入已有研究处理预算，不重扫股票、不改变截止、不借更换目录清零次数。

若研究更正发生在文章修订预算用完之后，仍应保存更正事实并标记该篇待继续处理，但本次自动运行不能无限生成新稿。不能带着已知错误发布。

### 3.5 部分完成不是部分发布

保留已完成的研究、文章和复盘，中断恢复只补缺失或失效步骤。是否可以正式保存或发布整份日报，继续服从原正式合同；本轮不新增“某篇失败就悄悄从名单删除”“其余文章先单独发布”的业务。

有一篇没完成，应报告“哪些已完成、哪些未完成、整份正式交付是否完成”，不能把技术失败当成空名单。

## 4. 机制二的实施：唯一当前含义，而不是仅缩短便笺

### 4.1 必须改实际输入

仅把 `research-handoff.md` 写短，却继续向作者提供夹有旧价格、旧判断和多轮争论的 `packet.json`、负责人答复、修订指令，这不算完成。

盘点作者实际能收到的**全部渠道**：任务提示、研究包、交接说明、原稿、修改意见、已处理问题、同股负责人答复及可读取目录。明确区分：

1. **当前判断与证据：**本轮正式采用的研究含义，作者据此写作。
2. **同一篇待修订原稿：**仅供编辑，不是现行条件的最高依据。
3. **内部过程记录：**保存用于复核，不继续作为给作者的并列投资结论。

当前有效说明中“确定”的是采用什么意见，而不是确定未来会涨。合理未知必须保留。

### 4.2 沿用现有交接，不新增永久角色

由原研究负责人在既有研究交付或一次必要的分歧处理后，整理当前说明。无变化、说明已清楚的股票直接复用，不为每只股票额外增加一次“润色交接”的模型请求。

沿用现有 `selection-handoff.json` 和 `authoring_note`，必要时从已验证的有效研究构造面向写作的材料视图。它是阶段材料，不是第二个事实仓。

程序只整理来源、筛选已确认有效字段、去除确定性重复，不用模板或代码生成投资解释，不自行判断哪些风险不重要。

### 4.3 说明至少交清的含义

不强制七个标题或固定字数，但应能从说明中找出：

- 当前意见、力度及适用的时点、价格与对象。
- 主要选择依据，以及为何是本股、为何是当前时点；原研究没有形成的说明明确缺失，不补造。
- 哪些财务事实只是经营背景，哪些变化直接支持当前判断。
- 最重要的反证及原研究为什么仍接受/不接受风险。
- 已知未知及其影响。
- 所有真正影响参与、等待、撤回或重新研究的条件。
- 本次采用证据的实际出处、统计范围与时间。

这张含义清单只用于检查材料完整性，不是要求作者每项都写一个段落，更不是要求对每只股票新增一套交易条件。

### 4.4 整理前后不得改变的内容

逐项对照意见、强弱程度、参考价、价格区间边界、时间身份、观察期与观察目标、最强反证、重要未知、条件逻辑及证据力度。

特别核对：

- “同时满足”不能变成“任一满足”。
- “收盘确认”不能变成“盘中触及”。
- “仅暂停新买入”不能变成“原推荐整体失效”。
- “尚未证实新增订单”不能变成“订单增长驱动”。
- “约20%的观察目标”不能变成可实现收益或估值结论。
- 区间包含端点、比较对象、复权口径、交易日/自然日不得丢失或被换用。

必要含义必须保留；重复句、已失效解释和内部管理说明可以合并或移出作者输入。

整理材料时发现原研究有实质矛盾，回到研究步骤记录变更，不得借“清理”悄悄改掉。材料整理对照测试中，研究含义必须固定，不能重新选股或改交易条件。

### 4.5 原始证据与当前说明的关系

保留原始材料和已有来源绑定。事实核对阶段必须能对照当前权威研究及必要原始证据，不能只检查“文章与已经被删漏的清洁说明一致”。

作者需要的事实可以从同一资料中提供明确来源的有限摘取；旧判断的历史版本留在内部归档，不再当成当前依据供料。不要篡改原始事实文件，也不要假称整理后的投影与原文件字节相同。

原有 trace 绑定、阶段输入身份和缓存识别继续使用；不得为本任务额外建设一套通用签名/哈希系统。

### 4.6 同一篇文章的修订规则

提供：当前有效研究说明、必要事实、同一篇原稿、集中修改事项。不给作者整段无关的内部争论。

要求作者：

> 按当前有效研究编辑同一篇完整文章。受影响的含义必须更新，未受影响的好内容保留。合并重复解释，检查全文的前后衔接；不是每解决一个问题就追加一段。不能为了好读改变事实、条件、反证或未知。

作者遇到关键研究缺口，沿用现有问题交付接口；不要在正文中自行推定答案。非必要细节可以不写，不能为填满话题无限补资料。

认可稿可作同一篇修订底稿，前提是身份、出处和实际用途明确。它不是同股新研究的固定答案，更不允许用旧稿旧条件替代本次新条件。

## 5. 机制三的实施：读者视角先行，事实核对随后

### 5.1 阅读审查是独立、干净的上下文

新建 `ops/recommendation-reader-check-prompt.md`，并新增相应材料构造分支。阅读审查只得到：

- 本次规范化后的待发表完整文章。
- 必要身份信息，默认只给股名与代码；日期只在正文已披露且确有需要时提供。不得把整个研究 identity 原样透传而额外注入参考价、目标、条件或文章未披露的投资判断。
- 现有通俗阅读标准的必要内容。
- 修订复核时，允许提供上轮仅基于正文形成的阅读问题、引句及编号。

不得得到：研究包、研究交接、原始事实库、同股负责人答复、原始投资审查过程、事实审查结果、采用/失败标签、此前不同版本正文、未用于展示的研究答案、可直接暴露上述内容的索引或工具。文件名、input-index中的来源说明、阶段提示和工具返回也属于实际输入范围，不能通过这些旁路泄露答案。

每轮阅读审查从未读过该股底稿的新上下文开始。不能复用已读过事实材料的审稿会话再声称“只看正文”。在文件模式下只建立本阶段目录和允许文件；使用既有隔离能力，验证实际可见上下文，不只依靠“请勿读取”。如果调用器会自动注入上层会话、其他文件或工具结果，先修正这一处，不另造操作系统级安全平台。

正文自带的来源引用可以保留，但阅读审查不访问其链接。

### 5.2 阅读审查的判断任务

可采用以下任务正文；执行者可针对已有字段接口作必要适配，不改变职责：

> 你只检查这篇文章对普通读者是否清楚、顺畅，不重新研究股票，不补充底稿中可能存在的理由。完整阅读一次，再指出影响理解的具体位置。
>
> 检查当前意见是否直接，主要理由如何支持意见，风险为什么没有推翻意见，参与和撤回条件是否需要在多处来回拼接。重复是否真的增加理解，抽象用语是否让读者自己翻译。文章长短本身不决定质量，开头概括后展开不自动算重复。
>
> 能总结出文章不等于文章好读。存在问题时引用实际原句，说明读者在哪一步会困惑，以及修改要达到什么目的；不要代写新的投资理由。没有影响理解的问题就通过，不为证明审过挑词。分清必须修改与纯偏好。
>
> 无法仅凭文章确认的事实不自动判假，只说明正文是否自洽或存在需要研究核对的歧义。不要凭自己的金融知识替文章补全结论。

沿用既有输出形态和字段，至少保留 `reader_summary`、`readability_issues`、`issue_checks`、`ready`；每个实质问题包括原句、问题、修改目的、`blocking`。不要另造100分评分器或词语黑名单。

### 5.3 事实核对的判断任务

使用独立后续阶段，调整现有 `ops/recommendation-review-files-prompt.md`。它读取：

- 与阅读审查完全相同版本的文章。
- 作者实际使用的当前有效说明及同版事实。
- 能够检查说明是否漏掉关键含义的权威研究内容及必要来源。
- 必须核对的实际研究变更及相关已处理问题，不把内部争论当作文章必须逐项复述的内容。

它检查事实、时间、比较口径、证据力度、主要反证和完整条件；不因“研究底稿里能解释”取消正文阅读问题，不替作者改稿。

保留已有 `fidelity_issues`、`research_issues`、`issue_checks`、`ready`。事实错误、条件变义或关键未知被删漏不能降为纯文风。

`validate_shared_material` 比较的是作者与事实核对使用的研究版本，不应要求阅读审查收到研究包。

### 5.4 集中反馈与采用条件

两个阶段都完成后，用确定性程序汇总意见，不增加一个“总审稿模型”。

- 阅读有实质问题，事实通过，也不能采用。
- 阅读通过，事实有实质错误或研究未决，也不能采用。
- 缺少一份有效审查结果，不能视为通过。
- 机器 `ready` 与问题条目矛盾时，不能只相信 `ready=true`。
- 两个阶段均通过，也只是程序具备采用条件，不冒称用户已经认可。

纯阅读问题集中给作者，事实误写也集中给同一作者；真正的研究问题交原负责人，不让作者自行改观点。

默认：每篇每次任务初稿后最多一次集中修订，修订稿再做阅读审查和事实核对。预算按同一任务和股票持续记录，不能通过换 stage 名、trace 版本、目录或“重新初稿”清零。沿用现有更严格限制；不提高已有研究澄清总预算。

删除冗余段落是合法修订。核销旧问题时，可以引用现文保留的有关内容和必要含义仍在的依据，不能强迫已删除的错误句必须继续出现。

### 5.5 缓存、中断、旧结果

在已有合同/阶段身份中区分阅读审查与事实核对，并更新受影响合同版本。不能把旧版“一次全材料审稿”的通过结果直接当作两步审查均通过。在顶层采用稿与 `accepted-recommendation.json` 的恢复验证处也要检查适用合同，不能只改阶段缓存，却让旧采用稿从顶层直接跳过新流程。已正式冻结的旧历史不因此被重写。

- 同版本文章和输入已完成，恢复时复用，不重新调用模型抽样。
- 阅读已完成、事实核对因传输失败未完成，恢复只补事实核对。
- 文章变了，旧阅读和旧事实审查均不能继续作为该新文的通过依据。
- 只更新其他股票的来源绑定，不应该重写本股；沿用并验证已有 `same_stock_material` 等能力。
- 旧任务正在执行或中断时，不自动跨合同恢复；本轮不切换生产版本。部署说明应写清如何让旧任务保持原版本完成或等待人工处理。

## 7. 真实模型验证：固定题目，不挑最好的一次

### 7.1 先冻结试验安排，再看结果

在第一次真实业务试验模型请求前，写入 `experiment-plan.json`，包含：

- 实际 baseline 与 candidate 代码提交、相关提示/指南/范文的版本。
- 每个样本的身份、研究截止、来源、完整性、用途和是否曾用于本轮调优。
- 各试验组唯一变化的因素、不变因素、次数和先后顺序。
- 对照评价标准、预计请求数、允许的一次修订和总请求上限。
- 每个 trial ID，以及 planned/completed/failed/interrupted/not_run 的记录方式。

同组A/B使用同一模型与设置、同一份研究含义、同一截止、同样范文、同样生成预算。先后顺序交错，例如第一轮A→B，第二轮B→A，减少时间顺序偏差；每次独立新上下文、独立 trial ID，不复用另一试验的完成缓存。固定随机标识只用于复现顺序，不能宣称模型输出完全确定。

**本轮最多64次真实业务模型阶段请求**，包含研究说明整理、负责人处理、作者、两种审稿、控制样本旧审稿及必要内容复核；不是每组64次。自动化单元测试的假模型不计。外层编码会话和仓库要求的一次独立方案审查不属于这64次业务试验，但应单独说明，不得把业务请求改名为编码来绕过计数。这个数是资源上限，不是统计学保证，也不是必须用满。

先按下面矩阵算实际预算并写入计划，优先复用已核实的研究和说明。超额需要另行授权，不可擅自改为批量同会话审稿、换弱模型、减少必要证据或偷偷扩大次数。

### 7.2 样本定位与原件核对

从当前本地有效归档与工作树中定位，不仅按修改时间挑文件：

**D1：飞凯材料复杂新版。**对应用户指出的“同一晚判断、次日参与”，以实际身份记录为准；特别防止把9月20日晚截止、9月18日行情形成日、9月21日参与日混成一个日期。找到完整新版研究、完整 WEB 对应正文及先前认可稿；截图只是定位线索，不能代替全文。

**D2：真实后续修订案例。**优先使用有完整同股当前意见分歧、原稿、负责人处理和修改后条件的捷捷微电案例；若该案例缺关键材料，按相同条件选择另一个已有真实修订案例并在试验前记录理由，不能根据试写好坏换案例。

**H1—H3：三个留出样本。**至少来自两只不同股票，且不使用D1/D2；优先三只不同股票、至少两个研究日，包含有条件参与、等待/不参与或复杂反证中至少两种。通过身份和来源元数据选定，不拿其正文来逐句调提示词。这里的“留出”指未用于本轮调优，不声称模型训练时从未见过。

C组审稿样本见7.5。对真实用户认可状态要能找到对应来源；没有用户认可证明，不得自行写 `user_approved=true`。

原件缺失时先完成实际本地查找；找不到才记录缺口。禁止根据本执行单的例句伪造历史文章、输入包或运行日志。关键样本不足，可以完成技术改造和可做的验证，但不能宣布业务验收通过。

### 7.3 A组：只检验研究说明整理是否改善初稿

- 样本：D1。
- A：当前实际旧供料方式，保留其真实重复但不人为恶化。
- B：整理后的当前有效供料。
- 两边研究结论、完整条件、必要未知、事实及范文相同；不使用更简单的认可稿研究替代复杂新版研究。
- 每边2次独立初稿，共4篇。此组不自动修稿，避免修稿掩盖初稿问题。
- 四篇均用同一候选版阅读审查和事实核对检查，输入不显示A/B名称、优劣预期或用户标签。
- 预计4次作者+8次审查=12次请求。整理研究说明若需要模型，单独计入总预算并保存实际输出。

输出比较：哪些重复减少、哪些逻辑衔接改善、哪些必要含义仍完整、是否有新遗漏。没有改善或只是变短，明确写无改善/证据不足。

### 7.4 B组：只检验集中修订交付是否减少“越改越差”

- 样本：D2。
- 使用完全相同的一篇原稿，以及同一组已经核实、确实需要改变的研究含义。
- A：原来实际的修改供料方式。
- B：同一篇原稿+整理后的当前说明+必要的集中变更事项，不夹带整段内部争论。
- 每边2次独立修订，共4篇，每次只修订一次。
- 两边都必须落实相同的实质变化，不能通过保留旧条件获得好文风。
- 四篇使用同一候选版两阶段审查。预计4次作者+8次审查=12次请求。

这组评价的是修改交付方式对文章的影响；机制一的调用先后主要由自动测试和整链回放验证。不能把这组结果夸称为已经单独证明所有顺序改变的因果效果。

### 7.5 C组：审稿是否识别真实好坏，而不是偏爱短文

四个固定正文，每个分别走旧的一次全材料审稿与新的两阶段审稿，各一次。每篇使用与自身版本匹配的研究，预计4×3=12次请求。

- C1：用户真实认可稿。认可证明只放评价台账，不提供给审稿。它检验阅读偏好识别，不自动证明其金融判断正确；事实核对须用该旧稿自身对应研究，不能拿新版条件判它错。
- C2：用户指出难读的完整 WEB 稿。不能在任务中告诉审稿“这篇必须不通过”。
- C3：篇幅较长但必要含义充分的真实候选正例。无用户认可证明时标为“参考标签未确认”，只能报告观察、待复核，不强造正确答案。
- C4：从已核实原文制作的明确标为**合成挑战**的版本：只把一个关键条件的“同时满足”改成“任一满足”，其余不变，保存原文与精确改动。它可以读起来很顺，但必须被事实核对拦住；不得要求阅读审查凭空知道原条件。

C组不改正文，也不重新研究。旧审稿通过/失败均原样保存。新审稿若仍漏掉C2，不修改提示再用同文反复重考，先记录本轮未达到预期。

### 7.6 D组：留出样本与实际衔接验收

候选实现及提示在A/B/C正式实测前冻结；实测后不得根据样本表现改写提示再把所有结果算成同一版本。H1—H3只用候选版各运行一次，按实际日常的初稿→两阶段检查→至多一次集中修订→两阶段复核执行。

三个样本初稿共9次作者/审查请求，最多三篇都修订再增加9次。为研究结论前置核对、必要说明整理及有限负责人处理保留余量，所有组总计不得超过64次。

至少一个留出案例走第8节的真实隔离入口回放，验证前置核对、供料、写作、审稿、保存与渲染的衔接。没有真实同股分歧的样本，不伪造分歧；相应分支由D2原始场景和自动测试补证，分别标明证据性质。

### 7.7 实验失败、限额、中断怎么处理

- 模型不可用或额度不足：保存当前材料和已完成产物，记录未完成；不自动换供应商。
- 传输中断：按已有可靠恢复机制继续同一次调用；终态内容不好不属于“中断”，不能当恢复重新抽样。
- 解析错误：保留原始交付；仅在可证明不改变模型判断时修复解析，不能人工伪造通过回执。
- 真实语义或写作失败：保留结果，不用同样输入反复重试至成功。
- 实测后发现确定性的接线/代码错误：可以最小修复，但涉及该错误的试验标为失效，并按新提交重新记录；旧结果不删除、总预算不清零。
- 修改写作提示、评价标准、样本或研究含义：属于新的实验版本，本轮不得未经说明继续无限调参。

## 8. 整链隔离验收：证明不是“试写有效、日常无效”

### 8.1 必须共用真实代码

沿用现有试写入口与 `run_article_cycle`。阅读基准中 `replay-files` 是 Astra 文件模式；某些旧 `run`/`check-review` 路径仍限制为 GLM。先读实际参数和策略，不使用 `run --provider astra` 猜测它能运行，也不删除旧路由保护只为让命令通过。

需要控制A/B输入或只跑单个阶段时，可在现有试验工具作最小扩展，或用本轮研究目录中的薄脚本调用生产共用函数。不得复制一套业务逻辑、为实验重新手写作者提示或另用模型直连绕开正式成稿入口。

### 8.2 正式入口回放的准确范围

在隔离根目录重放真实历史任务：读取当时已经存下的研究及复盘作为上游输入，不扫描当天全市场，不查询截止之后的信息。

从真实日常调度的相应入口执行候选路径。必须实际经过：研究级同股核对（有组合时）、当前有效供料、作者、干净阅读审查、事实核对、有限修订、最终文字核对、采用稿选择、原有保存/装配与正常渲染。

可以使用隔离数据根和已有上游交付作为回放输入；不能用假模型替代这条业务验收中的作者/审稿，不能跳过关键函数后手工写一个成功状态。自动测试里模拟供应商边界的结果，另列为技术测试，不能混成真实模型结果。

如上游是历史交付复用，要写“从已存研究/复盘交付开始的日常入口回放”，不能写“重新完成了五 Skill 的全市场正式日常研究”。真实生产任务仍然不启动。

### 8.3 页面只在隔离目录生成

使用原有渲染器和现有页面结构，在隔离目录或不占用生产服务的临时端口检查，不覆盖现有 `prism.html` 或公网文件。

检查：

- 最终采用稿、正式装配中的逐股正文、页面正常“研究说明/推荐理由”位置，是否对应同一内容。
- Markdown/HTML 标题和来源格式化属于既有显示转换，记录转换规则；不能靠删掉不同段落来让比对通过。
- 页面上没有新出现的修复说明、技术状态、原始JSON或另一套推荐内容。
- 原有D20、普通复盘、关键节点显示没有退化。

保存浏览器实际渲染截图和正文抽取结果。没有浏览器能力时，可以完成静态检查，但必须标记“浏览器未验收”，不能把一张自行拼的图当页面截图。

### 8.4 生产影响核对

前后核对实际生产目标是否被本实验写入：正式CSV、选股/复盘归档、必要索引、任务配置及WEB产物。对本轮关键文件使用已有校验或必要的小范围内容比对，不对全事实仓反复生成新哈希。

若生产任务自身并发写入，结合运行时间/来源区分，不能简单以文件变化认定本实验污染。不能辨别时报告未核清，不写“完全无影响”。

## 9. 如何判定结果：不把模型的通过当成用户认可

### 9.1 技术结果

T01—T27及实际相关测试通过，才能说程序行为达到本轮要求。基线已有失败、未运行测试、跳过测试、样本不足都单列，不隐藏。

### 9.2 内容结果

逐篇记录，不创建综合分数：

- 意见/事实/条件是否保真，关键反证和未知是否保留。
- 是否有影响理解的重复、抽象表达、前后折返或条件拼接。
- 是否完成交付，是否需要一次修订，是否修订后更差。
- 程序审稿是否放过被独立复核认定的坏稿；是否错误拦住好稿。
- 请求数、实际耗时、可获得的token用量；拿不到实际费用就写未提供，不能用猜测费用充数。

A/B两组分别呈现两次对照。只有看到具体改善、另一轮未出现明显反向退化且无关键含义损失，才可写“在本组小样本中看到改善迹象”。无差异、分歧或只有长度下降，写证据不足。这个判据是本轮工程判断，不是统计显著性证明。

C组：新流程应识别C2的真实阅读障碍，不能只因文章长而拒绝C1/C3；C4应被事实核对拦住。C3参考标签未确认时不计算“误拦率”。

H1—H3：均应在限定预算内交付，且无关键含义错误；出现未解决的实质缺陷或交付失败，本轮不能声称内容验收完成。

**最终阅读质量由 ChatGPT 阅读实际文章并与用户标准复核。**本地模型审稿只能提供意见，实施者不得给自己补填“用户已认可”或据此宣称根治。对好坏没有独立参考的文章，明确标签未确认，不捏造客观错误率。

### 9.3 最终状态只能据实选择

- `IMPLEMENTED_AWAITING_CONTENT_REVIEW`：实现和技术测试完成，真实样本已全交付，等待外部内容复核。
- `IMPLEMENTED_EVIDENCE_INCOMPLETE`：实现可检查，但额度、材料或环境导致业务证据不完整。
- `QUALITY_NOT_ESTABLISHED`：真实试验显示改善不充分或新流程仍存在关键问题。
- `BLOCKED`：存在无法在本授权内解决的具体障碍。

上述状态都不表示已部署。部署状态单独写 `NOT_DEPLOYED`，正式任务状态按实际查询记录，不擅自改变。

未达到目标时，将具体失败和可回退改动交清楚，不能继续扩大任务。小样本全部通过也不能写“从此不会再出问题”。

- 本机绝对路径及未经清理的全量终端/模型会话日志。
- 整个 `local_warehouse`、生产 `local_archive`、数据库、全部行情分区。
- 无权再分发的全文资料或商业数据批量；必要事实摘取附来源，受限制材料留本地并说明远端复核限制。
- 隐藏推理内容或不应公开的内部模型信息；只交可见任务、工具输入输出中允许公开的必要部分、实际文章和执行摘要。

不得为上传样本修改全局 `.gitignore`，不得 `git add -f local_archive`。

只做机械脱敏：本机路径换成相对路径/环境变量，秘密值移除。**股票代码、市场事实、价格、日期、条件、文章措辞不能以脱敏为由改写**，否则无法复核质量。脱敏映射保存在本地，公开 `delivery.md` 说明替换类别及是否影响可复现性。

若公开引用不足以核查某项关键结论，必须标记“远端证据不足”，不能只写一句“本地验证通过”。

### 10.5 代码也必须提交

同时提交：本轮实际代码、必要Prompt、自动测试、最小实验工具及必要运行文档。只提交研究材料而不提交实现，或只提交实现而不交全文证据，都不算完成。

提供每个改动文件归属机制一/二/三/衔接验证的说明。超出许可范围的修改独立列出原因；不得夹带未授权的选股或Web改造。

## 11. Git提交、远端验证和分支收尾

### 11.1 提交顺序与版本对应

可按基线测试/实现/证据形成少量有意义的提交，不追求很多提交。

正式真实模型实测前提交候选实现，使所有 trial 记录明确的 `tested_code_commit`。实测后提交证据。最终推送HEAD与测试代码提交之间，如果只增加本轮文档和实验结果，说明即可；如果动了影响执行的代码、Prompt或测试夹具，必须重新验证受影响内容，不能用旧测试证明新代码。

不要求某个文档写入“包含它自身的最终提交SHA”，避免自引用。`tested_code_commit` 写入材料；最终远端HEAD在给用户的回执里提供。

### 11.2 禁止的Git动作

- 不直接合并/推送到main，不force push，不删除旧分支。
- 不 `git add -A` 混入无关改动；只按审查过的具体文件列表暂存。
- 不替用户提交与本任务无关的未提交修改。
- 不把合成测试行情、试验文章写回生产正式记录。

### 11.3 推送之前与之后

推送前运行：

```bash
git diff --check
git status --short
git diff --cached --stat
git diff --cached --name-only
```

逐项检查暂存内容是否属于本轮；使用凭据时不输出其值。确认当前不是main后，只推本轮工作分支。

推送后实际查询远端分支SHA，例如：

```bash
git rev-parse HEAD
git ls-remote origin "refs/heads/$BRANCH"
```

核对两者一致，再检查复核入口和主要样本确实存在于远端提交。推送失败就如实报告，不能把本地commit当成已上传。

本轮不要求创建PR，更不要求自动合并。`conclusion.md` 写清后续审核通过时，应部署哪个准确代码版本，如何停止使用候选而保留原运行版本；部署与正式任务启用必须等用户后续明确授权。

## 12. 完成后给用户的回执格式

不要只回复“已完成，全部通过”。使用下面结构，条目下写真实结果：

### A. 结果

- 技术状态：按9.3据实填写。
- 三个机制各一句：实际改了什么、有什么证据。
- 内容质量是否已获用户/ChatGPT复核：未经复核就写“待复核”。
- 部署：`NOT_DEPLOYED`。
- 正式夜间任务与生产WEB：保持的实际状态，是否有任何变化。

### B. 代码与证据位置

- 仓库分支的实际链接。
- baseline SHA、tested code SHA、最终远端HEAD。
- `research/recommendation-reader-first-20260922/README.md` 的实际链接。
- 代码差异与完整文章入口的实际链接。

### C. 实际验证

- 自动测试：真实通过/失败/跳过数，日志位置。
- 计划试验数、已完成数、失败数、未运行数；实际模型请求数。
- A/B对照是否有改善，C组是否仍漏放，H组是否出现修订退步。
- 隔离日常入口与浏览器检查是否真实完成；上游哪些是历史复用。

### D. 剩余问题与运行影响

- 不超过必要数量的真实未决问题，直接指向文件/原句。
- 是否存在不可远端复核的材料。
- 日常流程多了哪些调用、减少了哪些返工，耗时证据与未确定部分。
- 下一步仅等待用户与ChatGPT复核，不自动开始今晚正式推荐/复盘。

## 13. 停止条件与不得偷换的验收

遇到下列情况要记录并停止相应部分，而不是换题：

- 不能定位可靠基线或关键原始样本。
- 实验会写生产目标且无法在授权内隔离。
- 独立阅读阶段仍会获得研究答案，却想只靠一句禁读提示宣布隔离完成。
- 为了清晰删掉了必要风险、未知或条件。
- 同样问题在本轮固定实测仍频繁出现，准备继续无限修改提示并只交最好稿。
- 请求总预算耗尽、模型无法使用或必要证据取不到。
- 必须修改五Skill投资方法、正式复盘方法、数据采集或Web结构才能继续。

禁止以下验收说法：

- “要求已写入，所以已经能稳定做到。”
- “所有模型都说通过，所以用户肯定会满意。”
- “文章比原来短，所以质量更高。”
- “换成旧认可稿，说明新条件也能写好。”
- “单项函数通过，等于日常任务和页面都通过。”
- “试验样本全部通过，说明已经根治、以后不会再出现。”

本轮合格的交付是：**改动与三个目标对应，实际输入和顺序可核验，所有样本原样可读，失败没有被隐藏，正式环境未被擅自切换，外部复核者能够判断这次到底改善了什么。**
