# V3 研究数据历史时间语义修复执行记录

**执行日期：** 2026-07-16

**迁移编号：** `2026-07-16-historical-time-semantics-v1`

**适用范围：** 统一研究事实仓、严格 `as_of` 查询和现有三类研究特征

**不在范围：** V3 选股、评分、报告、知识库、数据源和发布流程

## 1. 结论

本次修复已经把“本地何时收到数据”和“历史分析何时允许使用数据”分开，并且没有用 `trade_date` 绕过严格查询。

- 29 个数据集都有明确的业务时间、可用时间、接收时间、修订时间和严格回放等级。
- 只重写了 16 个数据集的时间治理字段；业务字段、业务键、业务哈希、分区路径和修订内容均未改变。
- 交易日历、行业日线和主题日线的历史首版事实按各自业务日 15:01（北京时间）保守重建。
- 当前证券主表、公司概况和无可靠发布时间的质押快照只从实际入库时间起可用，不倒填到历史。
- 公告保留官方毫秒时间戳；财报、指标、预告、快报和公司事件继续按真实披露日或保守披露边界截断。
- 分类关系的未来 `valid_from` 不可见；未来才会知道的 `valid_to` 在边界到达前被遮蔽。
- 2025-08-15 的真实严格复算成功，当前 2026-07-13 至 2026-07-16 的日报派生结果也已按新事实文件重新计算并读回。

这使通过严格时间合同的数据集可以用于 point-in-time 复算，但没有历史版本或真实发布时间的事实仍然 fail closed。2026-07-16 以前已经冻结的首批历史验证仍是“伪样本外回放”，不会追溯改名为严格回测。

## 2. 问题与根因

### 2.1 原始问题

历史交易日历的业务日期覆盖 2021-07-14 至 2026-07-16，但迁移前最早 `available_at` 是 2026-07-13。严格使用 2025 年 `as_of` 时，查询器因此正确返回空集，研究特征随后报交易日历字段缺失。

行业和主题日线存在同类问题：历史行的业务日期从 2025-07-02 开始，但整批记录被标成 2026-07-13 才可用。

### 2.2 代码根因

1. `ResearchBackfillService.backfill_market_core()` 把整次回填的 `through` 收盘时间作为所有历史日历行的批次默认 `available_at`。
2. `ClassificationBackfillService` 虽按 `trade_date` 分区，仍把回填截止时间作为所有行业/主题历史行的默认可用时间。
3. `ResearchWarehouse` 接受批次默认时间，但没有按数据集合同区分首版和后来修订，也没有校验当前快照是否被错误倒填。
4. 查询层严格执行 `available_at <= as_of`，行为正确；错误在采集、标准化和写入语义，不在查询器。

本次没有把所有数据集视为同一问题。股票日线、复权、估值、涨跌停、指数、公告等原本已有各自的历史时间证据，只补合同和防复发逻辑，没有统一改成业务日期。

## 3. 时间字段正式合同

| 字段 | 正式含义 | 强制规则 |
| --- | --- | --- |
| 业务时间 | 事实描述的交易日、日历日、报告期或关系有效期 | 决定事实适用范围，不自动等于可用时间 |
| 来源发布时间 | 来源声明的首次发布或更新时间 | 有则逐行保留；本地时间不得冒充来源时间 |
| `available_at` | 严格历史分析最早允许使用该版本的时间 | 所有严格查询只通过此字段放行 |
| `ingested_at` | 本地实际收到该版本的时间 | 永久保留；来源时间缺失时是可审计的保守下界 |
| `revision_no`/版本 | 同一业务键内容变化的顺序 | 首版和修订分别定时；后来修订不得倒填到首版业务日 |

可用时间策略：

- `business_close`：确定性首版事实在自身业务日 15:01 起可用。
- `valid_from_close`：可审计的分类目录或关系在自身有效日 15:01 起可用。
- `next_morning`：滞后交易事实在下一日 08:00 起可用。
- `source_published`：使用逐行来源发布时间；只有日期时采用次日 00:00 的保守边界。
- `ingestion_cutoff`：无法证明历史发布时间的可变快照，只从本地实际收到时起可用。

修订规则：披露型修订使用其自身来源发布时间；其他后来变化优先用可信来源更新时间，缺失时使用本次 `ingested_at`。任何修订都不能因为其业务日较早而提前进入历史快照。

精度标签：`exact`、`minute`、`date_conservative`、`inferred_from_endpoint_policy`、`ingestion_cutoff`。标签描述证据精度，不改变原始业务内容。

## 5. 迁移策略与执行记录

### 5.1 安全策略

迁移逐数据集执行，不复制或重建整个仓库：

1. 在任何文件变更前，对全部目标数据集和修订链进行只读预检。
2. 每次只在 `.staging` 生成一个数据集的新文件。
3. 校验分区、行数、业务键、`business_key_hash`、业务字段、`payload_hash`、修订数量和修订内容守恒。
4. 用目录原子切换和 DuckDB 事务同步文件哈希及时间范围；任何失败都恢复原目录和元数据。
5. 如果自动恢复过程本身发生重命名失败，程序保留 `.staging` 中唯一的原始备份并报告准确恢复位置；同一迁移编号再次运行时先检测该备份并 fail closed，禁止清理备份、覆盖恢复现场或继续后续数据集。
6. 写入固定迁移回执和最终全仓清单哈希；重复执行必须重新核验仓库根目录、29 数据集审计、文件指纹和最终清单，漂移时 fail closed。

预检发现部分财务事实的历史 `revision_no` 不是按发布时间单调排列。这是旧回放顺序留下的编号事实，不属于本次时间语义修复。最终规则是：只有迁移确实改变 `available_at` 时才重算相邻可用区间；仅规范精度标签时完整保留既有 `valid_from`/`valid_to` 和修订编号，避免越界修改历史版本。

## 7. 无法可靠修复的历史缺口

以下缺口没有足够本地或来源证据，系统明确拒绝伪造精确时间：

- `security_master` 和 `company_profile` 只有 2026 年获取的当前快照，没有属性历史版本；2026 年以前不能用当前名称、地区、行业或状态解释历史。
- `pledge` 只有统计截止日，没有可信首次公开时间；只能从本地收到时起使用。
- `share_float` 缺公告日的记录只能在事件发生后保守使用，不能证明事件发生前已知。
- 行业/主题日线只从 2025-07-02 开始；更早板块价格历史不存在。
- 主题成分只从 2025-07-31 开始，且 43 个官方主题不公开成分。
- 供应商没有提供可用的历史分钟、Level 2 或账户身份事实；日线量价不能证明机构买卖身份。
- 公告库当前覆盖从 2025-07-13 开始；更早公告不能由现有本地事实补造。

依赖上述信息的历史分析必须显示限制或 fail closed。补齐这些缺口需要未来新增经批准的数据证据，不属于本次最小修复，也不能靠修改时间字段解决。

## 8. 对 V3 严格回测的影响

修复后，可以严格按历史时点复算：交易日历、行情、复权、估值、涨跌停、指数、允许的行业/主题事实，以及当时已经披露的公告和财务版本。

但“全证据、全时期”的严格回测仍不成立，因为当前公司属性、质押发布时间、早期板块/公告和历史分钟等证据缺失。正确表述是：

- 使用通过严格时间合同且覆盖充分的数据集时，可称 point-in-time 复算；
- 只要模型依赖任一缺口数据，就必须降级或 fail closed；
- 2026-07-16 前冻结的历史批次继续称伪样本外，不追溯升级。

## 9. 防漂移规则

1. 任何新数据集或新写入路径必须登记时间合同，不能只提供批次默认 `available_at`。
2. `ingested_at` 不得删除或改成业务时间。
3. 后来修订不得倒填到原业务日。
4. 披露型数据必须有逐行来源时间或明确的入库下界。
5. 查询层不得增加按 `trade_date` 绕过 `available_at` 的开关。
6. 时间迁移必须通过守恒、回滚、幂等和未来信息隔离测试。
7. 任何历史回测报告必须列出实际使用的数据集、严格回放等级和未覆盖窗口。
