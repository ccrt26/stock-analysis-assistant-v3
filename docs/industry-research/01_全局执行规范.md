# 热点反向穿透法：全局执行规范 V3.0

本文件由四个阶段 Skill 共同读取。用户日常只读逐步执行手册和人话报告。

## 1. 第一原则：研究先由 ChatGPT 定义，Codex 只接明确合同

- 安装、分支、目录、commit、push、实体映射、本地取数、计算和监控属于 Codex。
- 研究范围、精确命题、最终付款人、系统边界、节点、证据语义、公司关系、商业阶段、持续性、预期差和失效条件属于 ChatGPT。
- 用户只批准范围和资金行动，不填写产业研究技术字段。
- 安装完成后，第一个实质研究动作必须是 ChatGPT 起草研究启动包。
- Codex发现范围或产业字段缺失时，必须退回 ChatGPT，不得要求用户补写系统起点、终点、证据等级或业务模式。

## 2. 角色接力

- A：ChatGPT A1 → Codex A2 → ChatGPT A3。
- B：ChatGPT B1 → Codex B2 → ChatGPT B3。
- C：ChatGPT C1 → Codex C2 → ChatGPT C3。
- D：Codex D1/D2 → 重大触发交 ChatGPT D3 → 用户批准 → Codex留痕。
- 每次角色切换立即停止。A、B、C默认各只允许一次有限定向补查/纠正/补算。

## 3. 文件与远程可见性

- ChatGPT产出的人读报告、机读交接和证据清单由下一次 Codex步骤先原样保存，再执行本地任务。
- Codex不得改写 ChatGPT拥有的语义字段；发现冲突新增 conflict。
- 每个 Codex步骤必须 commit + push，并汇报远程分支、commit和运行目录，确保 ChatGPT能够从GitHub审阅。
- 只commit未push不算完成交接。

## 4. 三类正式文件

1. 报告：解释为什么、证据、反证、未知和结论；
2. YAML/JSON：告诉下一方对象、字段、公式、条件、频率和review_due；
3. CSV证据：保存来源、published_at、known_at、claim、support_scope、exclusion、等级和冲突。

不得只交Word，也不得只交JSON。

## 5. 字段所有权

- `research_id / version / as_of / theme / precise_thesis / final_payer / system_start / system_end / exclusions / user_questions`：ChatGPT起草，用户批准，Codex校验和保存，不改写。
- `node_id / product / specification / role`：ChatGPT定义，Codex只映射。
- `entity_name / aliases / ts_code`：ChatGPT提供线索，Codex补齐、消歧和去重。
- `evidence_id / claim / support_scope / exclusion / evidence_level`：ChatGPT。
- `published_at / known_at / valid_from / valid_to / review_due`：ChatGPT提供源时间，Codex标准化和维护。
- `local_financial_metrics / valuation / price_metrics / input_manifest`：Codex。
- `business_stage / sustainability / expectation_gap / monitoring_contract`：ChatGPT读取Codex结果后确定。
- `monitoring_state / triggered_at / latest_value`：Codex。
- `action_decision`：只属于用户。

## 6. 证据与点时

必须区分身份、能力、认证/试点、供货关系、订单、重复交付、收入、利润和现金。每条证据同时写“能证明什么”和“不能证明什么”。只使用 `available_at/known_at <= as_of` 的事实；缺失不等于零，无记录不等于不存在。

## 7. 缺失、冲突和版本

- 状态分开：`complete / partial / unsupported / query_failed / no_record / unknown`。
- 每次更新生成新版本，旧版本只读。
- Codex数值变化不自动改变ChatGPT产业状态；达到合同条件只生成触发包。
- 未知项必须保留，后续有证据再补，不得静默删除。

## 8. 计算准备与字段边界

- `complete / partial / unsupported / query_failed / no_record / unknown / not_applicable / true_zero` 必须区分；`true_zero` 只由同一报告期、同一合并口径的正式证据确认，跨期文件只能支持字段含义、列报方式或会计语义。
- B3只允许 `direct_calculable / range_calculable / condition_only / not_applicable` 四种计算准备状态。它们是 `calculation_scope` 的标签，不是公司级授权；`allowed_numeric_fields` 与 `must_remain_unknown` 可以同时存在，未列入允许清单的字段不得计算；`condition_only` 不得生成三套全空数值情景。
- 营运资金先保留应收、存货、合同负债、经营现金流和销售回款等基础项；综合项仅在适用字段完整、同一报告期且同一合并口径时计算。预收款只有另行列示且不与合同负债重复时才纳入。
- 亏损或TTM归母净利润非正时，PE按单项指标标为 `not_applicable`，不影响PS、PB和经营事实；行业相对收益和固定长窗口估值为可选比较项，不得阻断主流程。
- `not_applicable` 必须记录当前原因和 `reopen_condition`，并在 `review_due` 复核；它不是当前修复缺口，也不是永久删除。

## 9. 用户负担上限

- 第一次液冷试点由 ChatGPT按V3预填完整范围。
- 新主题时用户最多提供一句主题和期望观察期；其余范围由ChatGPT起草。
- 用户不编辑YAML/JSON/CSV，只阅读人话报告并批准、修改一点或停止。

## 10. 与现有股票助手边界

本流程是季度/半年产业研究和中期观察，不替代现有短周期股票研究总控。不得修改现有五个股票研究 Skill、数据schema、定时任务、Forward CSV、D20口径或价格场景来承载本流程。

## 11. 永久禁止

不固定公司数量；不从价格上涨倒推产业关系；不用总分补救硬门失败；不绕过授权；不建设全互联网爬虫和大平台；不自动买卖、决定仓位或承诺收益。
