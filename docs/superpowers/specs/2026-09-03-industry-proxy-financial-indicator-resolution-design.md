# 申万行业代理与财务指标版本消歧设计

## 目标与边界

本次只解决两个已经确认的数据问题：

1. 在不购买 Tushare `sw_daily` 权限的前提下，用现有申万一级行业成分、个股日线和每日指标计算可回放的申万行业代理收益，恢复行业研究输入。
2. 对 `fina_indicator` 同一业务键、同一披露时点返回多个版本的情况，使用 Tushare 官方 `update_flag` 选择唯一修订版，补回可确定的财务指标事实。

不新增定时任务，不恢复旧评分体系，不引入非官方数据源，不伪造官方申万指数点位，不改变财务指标业务键，也不为极端情况建设新的通用版本平台。

## 一、申万一级行业代理

### 根因

`index_daily` 的接口合同不包含申万指数。仓库旧数据虽然以 `index_daily` 作为来源标记，但当前接口已经无法取得这些代码；`sw_daily` 才是官方申万日行情接口，而当前账号没有所需积分权限。因此，继续把 `index_daily` 当作申万官方日线既不可持续，也会误标数据语义。

### 计算方法

对交易日 `t`、申万一级行业 `g`：

```text
weight(i,t) = free_share(i,t-1) × close(i,t-1)
proxy_return(g,t) = Σ[weight(i,t) × pct_chg(i,t) / 100] / Σ weight(i,t)
```

- 成分关系按 `t` 当日有效的申万分类关系冻结。
- 用官方证券主表的上市/退市生命周期排除陈旧成分；仍上市但缺少行情的成分保留在覆盖率分母中，不降低 80% 门槛。
- 权重只使用前一交易日可得的自由流通股本和收盘价，避免使用当日收盘后才形成的信息给当日收益倒填权重。
- `available_at` 取本次计算实际使用的全部输入中最晚的可用时间。
- 证券主表优先取交易日当时已知的版本；只有早于建仓的历史日期使用首个可用快照，并同步后移代理 `available_at`。不能把后来修订倒灌进当日研究，也不能让最新主表更新任意推迟已有历史事实。证券主表纳入输入清单，重复计算使用稳定截止时间。
- 复用现有行业特征的 80% 成分覆盖门槛；覆盖不足时不生成可用代理事实，并登记真实缺口。
- 代理只表达行业收益，不构造或猜测官方指数点位、成交额、换手率等字段。

### 精度依据

最终时点安全版本在最近 250 个交易日中，与本地旧申万序列有 7,657 个可对照行业日样本。代理与旧序列日收益的相关系数为 0.9981，平均绝对误差约 0.049 个百分点，方向一致率约 98.59%，日度前五行业重合率约 96.19%。这是对本地历史序列的实测，不是对未来误差的保证，也不等于新取得了官方 `sw_daily`；所有输出必须明确标为代理。

### 存储和消费合同

- 新增独立事实集 `industry_daily_proxy`，不覆盖、续写或改名旧 `industry_daily`。
- 旧 `industry_daily` 保留为历史遗留事实，不再作为当前行业研究就绪条件，也不把旧来源标记改写成官方 `sw_daily`。
- 代理来源固定为 `local_derived`，端点/方法标识固定为 `sw_l1_free_float_proxy_v1`，公式版本固定为 `sw-l1-free-float-proxy-v1`。
- 业务键为 `(trade_date, industry_code)`；记录行业名称、代理收益、有效成分数、总成分数、覆盖率、权重日期和输入追溯信息。
- 行业热点特征新增明确的 `proxy_index_return_*`、`proxy_relative_return_*`、`proxy_index_status` 和 `proxy_method` 字段。代理值不得进入 `official_index_*` 字段。
- 行业热点公式版本升级，市场、公司和价格研究合同不随本次改动扩张。

### 任务接入

沿用现有收盘数据采集和晚间分类刷新任务：个股日线与每日指标落库后，计算当日行业代理；现有次日补偿流程继续重试缺口。不增加新的调度项。

当代理成功生成后，用“替代能力已就绪”的显式方式关闭原申万行业日线缺口；不把代理记录伪装成对原 `index_daily` 或 `sw_daily` 请求的成功响应。

## 二、财务指标业务键消歧

### 根因

当前业务键 `(ts_code, report_period, report_type)` 是正确的，缺失不是键设计错误。真正原因是 Tushare 对同一报告期和同一公告日可能返回初始版与修订版，而默认返回字段没有 `update_flag`。现有时点安全逻辑看到同一可用时间的两个不同内容后拒绝任选，因而将这些记录登记为冲突而不落库。

### 解决方法

1. 正常 `fina_indicator` 请求保持不变。
2. 只有响应中出现同一 `ts_code + end_date + ann_date` 的多个不同版本时，才以同一查询条件追加一次请求，并在原返回字段基础上请求官方 `update_flag`。
3. 若同组恰好只有一个 `update_flag=1`，选择该修订版；写入前去掉 `update_flag`，避免把供应商元数据本身当作财务业务字段。
4. 修订版不能倒填为原公告日已知。其 `available_at` 使用本次实际观测/入库时间，并保留现有时点精度标记。
5. 若没有唯一的 `update_flag=1`、仍有多个修订版或接口没有返回标记，继续保留冲突和缺口，不猜测版本。

该方案不修改业务键，不降低时点安全要求，也不会给没有重复数据的普通请求增加额外调用。

## 三、修复范围

- 行业代理：计算健康检查所需的最近 250 个交易日，并精确覆盖当前已知缺口交易日 2026-08-26、2026-09-01、2026-09-02。
- 财务指标：重试全部未解决的财务指标冲突业务键，而不是只重试当前事实表中缺失的键；这样能同时处理“已有旧事实但查询仍被冲突阻断”的键。
- 派生数据：重算受影响的 2026-08-26、08-27、08-28、08-31、09-01、09-02，保证滚动窗口和日报读取到一致结果。
- 修复前沿用现有备份机制；修复脚本保持可重跑，已有相同事实不重复写入。

## 四、验收标准

1. 截至 2026-09-02，最近 250 个交易日的申万一级行业代理满足合同和覆盖门槛；2026-08-26、09-01、09-02 不再因申万官方接口不可用而阻断行业研究。
2. 研究输出只出现明确的代理字段和方法说明，不把代理称为官方指数或官方行情。
3. 所有能由唯一 `update_flag=1` 判定的财务冲突完成落库和冲突关闭；无法判定的键仍被准确列为未解决，不通过任意选行掩盖。
4. 现有业务键、旧事实和历史来源均未被破坏或改写。
5. 相关单元测试、集成测试、健康检查和缺口审计通过；最终报告列出已关闭缺口、剩余缺口及其真实原因。
