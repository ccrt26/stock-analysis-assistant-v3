# 研究数据缺口闭环设计

> 历史记录：本文保留当时方案与事实，不作为当前运行入口或调度依据。当前时序以 `docs/architecture/current-v3-architecture.md` 和 `ops/forward-selection-prompt.md` 为准。

日期：2026-09-03

## 目标与边界

目标是让每日三次数据任务能够回答三个问题：某交易日应有什么、实际有什么、没有时属于可补缺口还是明确受限；并修复截至 2026-09-02 已确认的可修复缺口。

本次不恢复旧评分、Gate 或关注池，不增加定时任务，不引入非官方数据源，不降低 `available_at <= as_of` 的时点安全标准，也不改变五个选股 Skill 的职责。

## 科学的判定模型

每个应采集的数据集×交易日必须落入且只落入一个可解释状态：

- `complete`：预期数据已落库并通过完整性检查。
- `legitimate_empty`：官方接口成功返回空，且业务上允许当天无记录，例如无停牌。
- `waiting_upstream`：处于该官方数据通常尚未发布的时间窗口。
- `permission_denied`：正确官方接口明确拒绝当前 Token。
- `unsupported_optional`：可选能力当前不受官方接口支持，不能冒充核心缺口。
- `provider_conflict`：同一业务键和公开时间出现多个不同载荷，无法在不猜测的情况下选定版本。
- `failed`：网络、解析、校验或写入失败，可重试。
- `unclassified_missing`：应该有但没有、且尚未查明原因；这是健康检查必须报警的真正盲区。

健康检查的核心不是“文件是否存在”，而是用交易日历枚举应有日期，再把事实分区、合法空记录、缺口登记、权限状态和冲突登记做差集。完整历史模式从每个数据集可证明的起始覆盖日检查到指定截止日；分钟数据单独按“代码×交易日”检查，不混入日频核心完整率。

## 已确认根因与处理

| 问题 | 根因 | 处理 |
|---|---|---|
| 行业日线停在 8/31 | 误用通用 `index_daily`；官方文档明确其不含申万行业，偶发返回不能作为契约 | 改用官方 `sw_daily`；只写已发布的申万一级代码。当前 Token 若无权限，登记 `permission_denied`，不伪造完成 |
| 8/26 主题、停牌缺失 | 当晚任务被 CNINFO 分页异常中止，次日流程未补跑这些阶段 | 精确补 8/26；主题走 `index_daily`，停牌走现有 `suspend_d`，官方空结果记 `legitimate_empty` |
| 8/11 融资融券缺失 | DuckDB 被另一个进程占锁，任务在创建运行记录前退出 | 精确补 8/11，并把全局任务锁提前到仓库初始化之前，数据库连接增加短时有界重试 |
| 8/26、9/1、9/2 行业缺失 | 8/26 为任务中断；9/1、9/2 为错误接口无申万数据 | 切换正确接口后精确回补；无权限则保持显式权限阻塞 |
| 601 个财务指标业务键歧义 | 同一业务键、同一 `available_at` 有多个不同官方载荷，且缺少可证明的版本顺序 | 保留全部冲突变体和哈希；不猜最终值、不推进该端点水位、不删除暂存；只在官方字段或后续修订能唯一确定时解决 |
| 分钟数据大量不完整 | 官方接口对当前权限/频率有限，现有分区存在并不代表每个代码完成 | 作为可选能力按代码日检查，区分完整、权限/限频和未采集，不影响核心日线结论 |
| 孤儿运行、错误退出码 | 进程异常后 `running` 未收口；close 阶段用晚间派生就绪度决定退出码 | 获得全局锁后把无活动执行者的旧 `running` 标为 `interrupted`；各阶段按自身职责决定退出码 |

## 存储设计

沿用 `research_data_gaps` 记录日期/能力级状态，不以空 Parquet 假装数据存在。将 schema 升至 v5，新增 `research_fact_conflicts`，至少保存：数据集、分区、业务键哈希及 JSON、载荷哈希及 JSON、来源、端点、`available_at`、冲突状态、首次/最后观察时间和解决说明。唯一键为“数据集×业务键哈希×载荷哈希”，保证重复执行幂等。

现有 `research_data_gaps` 的登记与消解集中到共享组件：成功事实分区可消解可重试缺口；合法空、权限阻塞、可选不支持、提供方冲突必须由相应证据显式消解，不能仅因别的数据文件存在而清除。

财务冲突继续遵守保守规则：`update_flag` 只作为来源字段保存，官方合同没有赋予它数值优先级，不能用“取最大值”猜正确版本。同一业务键在同一可用时点只有一个规范化载荷时才可直接采用；否则持久化所有变体、标记 `provider_conflict`，该端点不写完成水位且保留重跑所需信息。433 个默认范围内键只是 601 个冲突键中落在默认选股股票范围的子集，不代表 433 个股票所有财务数据都缺失。

查询层按时点屏蔽冲突键：冲突被首次观察后、在有可审计依据解决前，该键不作为确定事实返回；冲突解决只对解决时点及以后生效，不能把后来知道的结论倒灌到更早的 `as_of`。派生查询和输入清单哈希均使用屏蔽后的事实视图。

## 采集和运维设计

行业日线单独调用 `sw_daily(trade_date=YYYYMMDD)`。字段映射遵循官方单位：`pct_change -> pct_chg`，`vol` 从万股换算成股，`amount` 从万元换算成元；保留来源和可得时间，先校验代码属于当前申万一级目录再提交。主题仍使用 `index_daily`，避免两个概念再次共用错误接口。

三次日任务在打开 DuckDB、初始化 schema 或创建 `ResearchWarehouse` 之前获取同一全局写锁。锁只串行化仓库写入，不改变任务时刻。DuckDB 冲突仅对明确的 lock/busy I/O 错误做短时、有上限的重试，其他错误立即抛出。获得锁后、创建新 run 前，可安全地把更早的残留 `running` 运行原子标为 `interrupted`。

close 阶段只以收盘阶段数据采集结果作为退出依据；evening 和 next-morning 才检查各自应生产的派生数据。可选分钟能力的受限不使核心日线任务失败，但必须进入健康报告。

## 真实修复顺序与验收

1. 先上线缺口分类、连续性健康检查和冲突账本，使每次修复可复核。
2. 切换申万正确接口并探测权限。若无权限，停止行业伪回补并输出唯一外部阻塞。
3. 精确补 2026-08-11 融资融券、2026-08-26 主题和停牌、2026-08-26/09-01/09-02 行业；只重算受这些日期影响的派生结果。
4. 对已识别的财务指标歧义做定向重取和冲突持久化，不降低时点安全。
5. 收口分钟能力、锁冲突、孤儿任务和阶段退出码。

验收以指定截止日 2026-09-02 的合同窗口健康检查为准：核心日频五年、行业/主题/两融 250 个交易日、停复牌一年、分钟 20 个交易日×冻结股票范围；其他非日频数据按自身报告期和有效区间检查。所有必需单元要么完整、要么有证据支持的合法空或外部阻塞；不得存在未分类缺失；物理文件、来源端点、哈希、行数、业务键和修订区间通过检查；受影响派生日期重算成功；测试证明重复执行幂等。若 `sw_daily` 权限仍未开通或财务提供方冲突仍无确定顺序，最终报告必须把它们列为未关闭项，而不能宣称“全部补好”。
