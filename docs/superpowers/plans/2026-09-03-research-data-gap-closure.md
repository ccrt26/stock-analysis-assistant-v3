# 研究数据缺口闭环实施计划

> 历史记录：本文保留当时方案与事实，不作为当前运行入口或调度依据。当前时序以 `docs/architecture/current-v3-architecture.md` 和 `ops/forward-selection-prompt.md` 为准。

> 执行时使用 `superpowers:executing-plans`，严格测试先行；设计依据见 `docs/superpowers/specs/2026-09-03-research-data-gap-closure-design.md`。唯一一次独立审查结论为“通过（以修订版为准）”，下列内容已吸收该修订并拥有执行优先级。

目标：修复健康检查盲区和已确认的可修复缺口，并将正确官方接口的权限阻塞、财务版本冲突及可选分钟受限准确呈现。

## 1. 缺口与冲突存储契约

- 为共享缺口登记/消解行为先补单元测试，覆盖幂等、状态转换和不能误消解的状态。
- 为 schema v5 的 `research_fact_conflicts` 先补迁移和存取测试；v4→v5 必须是显式且可重复执行的迁移，不能只改版本号。
- 将缺口当前状态唯一键改为 `(dataset_id, partition_value, scope_key)`，补齐来源、端点、详情、复查/重试/解决时间；实现共享缺口组件、冲突表和最小仓库 API，保持现有 Parquet 事实格式不变。
- 只有相同数据集、分区、scope、来源和端点的成功验证才能消解失败或权限缺口；`legitimate_empty` 必须保存官方成功响应证据，`waiting_upstream` 必须有到期时间。

## 2. 基于交易日历的健康检查

- 先写失败测试：日频分区中间断日必须被发现；合法空、权限、等待和冲突要分别归类；分钟按代码日单列。
- 实现从交易日历推导“应有集合”：核心日频五年，行业/主题/两融 250 个交易日，停复牌一年，分钟 20 个交易日×冻结 scope；非日频数据使用自身合同。
- 完整必须同时验证 manifest、文件、内容哈希、行数、字段、业务键和来源端点。历史 `index_daily` 申万分区在重取验证前不得静默视为合格。
- 报告展示每类日期/键的数量、来源、端点、scope 和证据摘要；`resolved` 不计入当前缺口；`complete_core_date` 继续只是诊断信息，不恢复为 Gate。

## 3. 申万行业正确接口

- 先写客户端与归一化测试，固定 `sw_daily` 端点、字段名和单位换算。
- 将行业日线从 `index_daily` 拆出，主题保持原端点；为分类、主题、停牌、两融增加数据集级定向修复入口。
- 对空、权限、限频、失败分别登记，不再把“过滤后 0 行”当无声等待。

## 4. 财务指标歧义闭环

- 先写测试证明：不可判定变体全部持久化、标记冲突、不推进端点水位、不删除重跑依据；`update_flag` 无论数字与否都不能作为优先级；可唯一判定时正常提交。
- 对已识别业务键仅重取 `fina_indicator`，避免重复调用无关六个端点。
- 查询层按 `first_seen_at`/`resolved_at` 屏蔽未决冲突，解决不能倒灌；派生输入与哈希使用屏蔽后的事实。
- 输出 601 个历史冲突键与默认范围内子集的最新可复核统计；若官方返回已收敛，按证据解决，否则保留冲突。

## 5. 任务互斥、孤儿运行、分钟能力与退出码

- 先写测试覆盖仓库初始化前获取锁、连接有界重试、旧 `running` 收口、各阶段退出规则。
- 将 CLI 三次写任务的同一全局锁移到打开 DuckDB/初始化仓库之前；拆分已持锁和未持锁入口避免重入死锁。
- 获得锁后、创建新 run 前，把更早仍为 `running` 的运行原子收口为 `interrupted`；连接只对明确 lock/busy 错误做有界退避重试。
- 分钟健康按代码×日期判断，权限/限频登记为可选受限。
- close 只按 close 阶段职责退出，evening/next-morning 分别验证自己的产物。

## 6. 修订区间异常

- 先复现 `688668.SH` 零长度旧修订区间的校验失败。
- 仅处理已核实的 `688668.SH`、报告期 `2026-06-30`、目标 business key 的零长度 revision；先把冲突变体纳入账本，再修正经证明无效的 revision，保留当前有效事实且未决期间由查询层屏蔽。
- 重跑修订完整性检查。

## 7. 回归测试与运维说明

- 运行相关测试集，再运行全量测试。
- 更新数据运行手册，说明状态含义、权限开通后的重跑命令、冲突处理和阶段退出码。

## 8. 真实数据精确修复

- 在全局锁内 checkpoint 并关闭连接，先 dry-run 输出精确目标，再备份元数据库和会覆盖的 Parquet；记录不存在的新分区、SHA-256、行数、相关 metadata/revision/gap/conflict/watermark 基线和输入参数。
- 精确补：`margin_detail` 2026-08-11；`theme_daily`、`suspension` 2026-08-26；`industry_daily` 2026-08-26、2026-09-01、2026-09-02。
- 定向重取已识别的财务指标冲突键；不执行全仓无差别重抓。
- 按 82 交易日依赖窗口检查实际存在的受影响派生日期，至少覆盖 2026-08-26、08-27、08-28、08-31、09-01、09-02；不依赖两融/停牌的特征不盲目重算。重复执行一次验证幂等。

## 9. 最终验收

- 以 2026-09-02 为截止日运行合同窗口健康检查，核对日频连续性、分钟冻结 scope 覆盖、缺口分类、冲突账本、来源端点、文件/哈希/行数/业务键和修订区间。
- 核查三次任务最近运行和退出状态，不留下无执行者的 `running`。
- 分开汇报“已补齐”“合法空”“权限阻塞”“提供方冲突”“可选能力受限”。只有没有未分类缺失且所有可修复项均关闭时，才声称补齐完成。
